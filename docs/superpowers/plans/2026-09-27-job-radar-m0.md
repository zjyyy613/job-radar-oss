# Job Radar M0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a first usable Job Radar that ingests real internship/campus jobs from job-pro plus NCSS, normalizes and conservatively canonicalizes them, extracts qualification gates once per changed JD, and lets a guest user browse real jobs with explainable qualification results.

**Architecture:** External sources are isolated behind adapters that emit one Job Radar `SourceRecord` contract. Source records are normalized into conservative `CanonicalJob` records; only new/changed jobs enter the gate-extraction pipeline. User profile stays local-first in M0, while a deterministic qualification engine combines local profile + persisted gates at render time.

**Tech Stack:** Next.js 16, React 19, TypeScript, Tailwind CSS, shadcn/ui, Supabase PostgreSQL, nuqs, DeepSeek Responses API, Node.js scripts, GitHub Actions, pinned `@ha7ch/job-pro@1.2.1`, pinned JobHunter commit for NCSS.

**Spec:** `docs/specs/job-radar-product-spec-v1.0.md`

## Global Constraints

- Product is guest-first; no authentication is required in M0.
- Qualification and preference fields are separate; preferences never produce `Blocked`.
- Ambiguity or missing user data returns `Check`, not `Blocked`.
- Only explicit required + clear contradiction returns `Blocked`.
- Preferred requirements never block.
- Evidence is verbatim source text; the model must not invent evidence.
- Source failure is `Unknown`, never automatically `Closed`.
- Gate extraction runs only for new or content-changed canonical jobs.
- No embeddings, vector search, application tracker, auto-apply, resume generator, account sync, or admin dashboard in M0.
- External source implementations are pinned; upgrades require smoke tests.
- Keep files small and responsibility-focused; no monorepo.

## Review Focus

1. A source fails mid-run: existing jobs remain browsable and are not mass-marked Closed.
2. Two similar cross-source postings conflict on recruitment batch: they remain separate rather than being wrongly merged.
3. A user omits `days_per_week`: jobs requiring days/week become `Check`, not `Blocked`.
4. An LLM extraction returns malformed or unsupported gate values: validation rejects the extraction and preserves the previous valid gates.
5. A job JD is unchanged between runs: no new LLM extraction occurs.

  - Batch conflict => do not merge.

  - Failed source run => existing job remains Unknown/current state, not Closed.
  - One successful missing run => increment missing count, not Closed.
  - Two successful authoritative missing runs => Closed.
  - Explicit upstream Closed => Closed immediately.

- [ ] **Step 3: Implement conservative canonicalization**
  - No embeddings.
  - No LLM merge decision.
  - Return a merge trace/reason for every automatic merge.

- [ ] **Step 4: Run tests**

## M0 stop rule

M0 is complete when all seven tasks pass and one real user can:
1. enter the app without an account,
2. create a minimum qualification profile,
3. browse jobs from both job-pro and NCSS,
4. see conservative qualification results,
5. inspect verbatim evidence,
6. read a full JD,
7. open the official application source.

Do **not** add Saved, Hide, Seen/New, Compare, account sync, landing page, semantic search, notifications, application tracking, or UI redesign before this stop rule is met.

## M1 immediately after M0

Only after real M0 use:
- Saved
- Hide + Undo
- Seen/New
- inline profile completion
- fuller empty/error states
- mobile/accessibility polish

## Recommended execution order

Execute Tasks 1 -> 7 strictly in order. Each task must end with tests passing and a commit. Do not start the next task while the current acceptance condition is unresolved.
